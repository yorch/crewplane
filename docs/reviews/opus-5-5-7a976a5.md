## Remaining and new findings

### P2

#### R1. [P2, new] One blank-titled task card stops all orchestration

- **Location:** `src/engine/read-model.ts:42, :202-270`; `dashboard/graph-builder.ts:61-62, :96-109, :139-144`; `supervisor.ts:39, :405, :535-546, :914`
- **Scenario:**
  1. A committed card begins with a blank line, or its first line is only `#`. `assign` accepts this because it only checks the owner regex (`agents.mjs:730-736`).
  2. `parseTask` produces `title: ""`, because `??` does not catch an empty string.
  3. `buildGraph` requires a non-empty label and throws, so `snapshot()` rejects.
- **Consequence:**
  - A running supervisor logs "Board temporarily unavailable" forever and launches nothing, while its heartbeat stays fresh.
  - A new `start` faults at `:405`.
  - Completing turns pause as "Result handling failed".
  - `/api/snapshot` returns 503 and `agent list` fails.
- **Root cause:** display validation sits on the authoritative board path. `CONTRACTS.md:5` and `EXTRACTION.md:18` say the supervisor imports no dashboard code, but `read-model` imports `dashboard/graph-builder`, `dashboard/headless` and `watchdog/dashboard`. That holds for HTTP but not for dashboard projection code.
- **Fix:** fall back to the task ID for an empty title. Split the scheduler board from presentation projections, so a graph failure degrades only `graphs`. Correct the two docs if the import stays.
- **Regression:** a card with a blank first line and a live assignment still schedules, and the dashboard snapshot still returns with the graph marked unavailable.

#### R2. [P2, residual of #2] Checkpoint is refused while a third sibling is not ready

- **Location:** `agents.mjs:300-330, :976-992`; `orchestration.ts:326-344`
- **Scenario:**
  1. Lane `builder` has A `ready`, B `ready`, and C assigned but unclaimed, which `assign` allows.
  2. A correction on B leads to B `working`, then B `blocked` with no checkpoint.
  3. A correction then arrives for A.
  4. A is `OWNERSHIP_INVALID` because of B, so B gets a checkpoint-only turn.
  5. `agents checkpoint` runs `executionGuard(ctx, id, agent)` with `revision=false`, which requires every sibling to be `ready`. C is not, so the command fails with "already has active task C".
- **Consequence:**
  - A's correction never runs.
  - C also cannot claim while B is blocked, so its turns record no progress and pause the whole lane.
  - The only exits are releasing a sibling or submitting B as `ready` against the turn's instructions.
  - `blocked→working` hits the same guard.
- **Root cause:** the guard treats a checkpoint as starting new work, when it actually yields work. The exemption exists only for a `ready→working` revision.
- **Fix:** exempt `checkpoint` from sibling-state checks, keeping the running-record and worktree checks. Allow `blocked→working` when siblings are `ready`, checkpointed or unclaimed.
- **Regression:** extend `orchestration.test.ts:362` and `agents.test.ts` to three siblings, with both unclaimed and checkpointed-blocked third tasks.

#### R3. [P2, regression from #28] Pi receives a session directory the supervisor never created

- **Location:** `harness.ts:144-145`; `supervisor.ts:699-701, :741-745`
- **Scenario:** output moved to `<dir>/runs/<lane>/<id>.result.json`. `dirname(dirname(output))` is now `<dir>/runs`, so Pi gets `--session-dir <dir>/runs/pi-sessions`, while the supervisor creates `<dir>/pi-sessions`.
- **Consequence:**
  - The prepared private directory goes unused.
  - If Pi does not create the path itself, every Pi turn fails. That behaviour can't be verified statically.
  - A lane named `pi-sessions` passes `validId` and would share that directory with its logs, so pruning could reach session data.
  - No test references either path.
- **Root cause:** the session location is derived from the shape of the log path.
- **Fix:** pass an explicit session directory to the adapter, and reserve the name if it stays under `runs/`.
- **Regression:** assert that the path passed to Pi equals the directory the supervisor created.

### P3

#### R4. [P3, residual of #10] Retained process identity only blocks the same lane

- **Location:** `agents.mjs:802-811`; `orchestration.ts:414-422`; `supervisor.ts:607-618`; `watchdog/runner.ts:350-355`
- **Scenario:** a record is `paused` with `cleanupUnverified` or a retained PID. `release` passes because the status isn't `running`, and the overlap check ignores it too. Reassigning to another lane then launches while the old group may still be alive.
- **Consequence:** this contradicts "a live or unverified old child prevents replacement" (`USAGE.md:103`). Separate worktrees limit file collisions but don't prevent other side effects. The watchdog also leaves these groups out of `orphan-or-unknown-child`.
- **Fix:** treat `pid`, `processGroupId` and `cleanupUnverified` as occupied in all three places.
- **Regression:** release refused for a retained group, overlap blocked, and the watchdog reports the group.

#### R5. [P3, new] A verified deadline kill is recorded as unverified

- **Location:** `supervisor.ts:871-884, :897, :1068-1073`
- **Scenario:** at the deadline, timer T1 is stored in `drainTimer`. The leader exits and the `exit` handler overwrites `drainTimer`, so `finish` can't clear T1. If a SIGTERM-ignoring child keeps the sweep running past the grace, T1 sets `forcedDrain`, even though `close` already fired and SIGKILL verified the group empty.
- **Consequence:** a clean kill reports "Time budget reached", yet `retry` is then refused until `--confirm-cleanup`. It fails closed but gives the operator false information. `lifecycle-binary.ts:258-278` follows this exact path without checking the flag. A TERM-ignoring leader hits a similar false positive through T1.
- **Fix:** use separate timers, clear both, and don't set `forcedDrain` after `close`.
- **Regression:** the deadline fixture asserts `cleanupUnverified` is absent after a verified kill.

#### R6. [P3, new] Peer answers route correctly, but peer questions never wake the peer

- **Location:** `orchestration.ts:241-249, :287-294, :368-370`
- **Scenario:** B, blocked on task T, sends a direct question about T to peer lane C. C's events only include messages for C's own tasks, and reviewer lanes only take coordinator requests.
- **Consequence:** an idle C gets no turn and the coordinator gets no event, since the message isn't addressed to it. B's outbound wait suppresses its own retries. The test at `orchestration.test.ts:660` starts with both messages already present. Separately, an answer to a question sent without `--task` carries a null task and never resumes the owner.
- **Fix:** wake the addressee on an unanswered, task-scoped peer question, or notify the coordinator. Require `--task` for blocking questions from task owners.
- **Regression:** a peer question produces a candidate or coordinator event.

#### R7. [P3, residual of #26] `read-model` runs Git with the inherited environment

- **Location:** `read-model.ts:170-173`
- **Scenario:** with `GIT_DIR` set to an invalid path, `snapshot()` throws, causing the same outage as R1. With a valid foreign repository, branch labels are wrong. The test covers only `discoverProject`.
- **Fix:** pass `gitEnvironment()`.
- **Regression:** `snapshot()` under a foreign or invalid `GIT_DIR`.

#### R8. [P3, new] Dashboard hourly run count omits the retired ledger

- **Location:** `dashboard/headless.ts:102-106` versus `:176-178`; `dashboard.js:166`
- **Scenario:** after compaction, enforcement and `RATE_LIMITED` count retired runs, but `usage.runsLastHour` counts live records only. A rate-limited lane can display a low run count.
- **Fix:** reuse the combined `runs` value.
- **Regression:** retired runs in a headless projection test.

#### R9. [P3, new] Graph summary mislabels truncation

- **Location:** `graph-builder.ts:267-272`; `graph-renderer.js:90-91, :188`
- **Scenario:** `buildGraph` already slices to 50 nodes and 100 edges, so "Truncated" is always 0. Truncated items appear under "Archived/hidden upstream", and edges to truncated nodes show as "Missing reference".
- **Fix:** return truncated and archived counts separately, and drop or label edges to truncated nodes.
- **Regression:** 60 active tasks render the correct split.

#### R10. [P3, residual of #21] A stop issued during startup is silently dropped

- **Location:** `supervisor.ts:385-407, :439-445`; `cli.ts:208-212`
- **Scenario:** the new generation exists only in memory until the first save, which happens after the board read. A `stop` in that window reads the previous generation, reports `queued`, and is discarded while the supervisor keeps running.
- **Fix:** save the generation before accepting commands, or accept a previous generation when `at >= startedAt`.
- **Regression:** barrier the first save, queue a stop, assert the drain.

#### R11. [P3, documented limit made more reachable] Board lock has no owner or recovery

- **Location:** `agents.mjs:380-407`; `cli.ts` installs no signal handling for `agents`; `supervisor.ts:885-890`
- **Scenario:** `send` now takes this lock, and group cleanup now sends SIGTERM to members. A CLI call interrupted mid-mutation exits without its `finally`, leaving an empty directory. Every later mutation then fails, and nothing identifies the owner. `CONTRACTS.md:7` documents manual inspection, but gives the operator nothing to inspect.
- **Fix:** use `withProcessLock`, which already provides liveness-verified recovery.
- **Regression:** a killed lock holder is recovered, and a live holder is respected.

#### R12. [P3, residual of #16] Compiled acceptance omits an in-flight drain and post-crash recovery

- **Location:** `tests/lifecycle-binary.ts:195, :218, :235-239`
- **Evidence:** SIGTERM is sent only to an idle supervisor. Each `stop` comes after the turn settled. The restart test covers refusal but never the follow-up where a dead group produces a paused record and a preserved session on retry.
- **Fix:** add a compiled scenario with SIGTERM during a running turn, asserting that completion and trace settlement precede lease release, plus a dead-group restart and retry.

#### R13. [P3, residual of #23] A newly created parent directory is not durable

- **Location:** `io.ts:21, :31`
- **Scenario:** the first write into `tasks/<id>/` syncs only that new directory. Power loss can remove a reported assignment because `tasks/` wasn't synced.
- **Fix:** sync newly created ancestors up to a known root.
- **Regression:** assert the sync sequence through a filesystem seam.
