## CLI installation and self-update

`install.sh` and `crewplane update` share one release contract: a platform asset plus a sibling `.sha256`. The installer accepts `--version`, `--dir`/`--prefix` (both `VALUE` and `=VALUE` forms), `--dry-run` and `--help`, normalizes `uname -m` to the published asset names, retries transient downloads, enforces `https` for custom sources, stages inside the target directory, verifies the checksum and the staged binary's reported version, and renames atomically. It refuses unwritable directories instead of escalating to sudo, handles signals explicitly, and reports upgrades, PATH hints, shadows and non-sticky pins. Source tests execute the real script against a local fake release server for install, upgrade, pinning, argument forms, spaces in paths, CRLF and foreign-name checksums, mismatch, missing asset, failed lookup, unwritable directory, dry-run, bad arguments and staged-file cleanup.

`crewplane update`, `--check` and `--force` verify the published SHA-256, the executable header and the staged binary's `--version` before an atomic same-directory rename, preserving the existing mode and refusing symlinks, non-files, foreign owners and unwritable directories. Failures print a JSON outcome and exit non-zero. Release metadata and assets are read with streamed size caps; API requests accept only `https` (loopback excepted) and send credentials solely to `https://api.github.com`. The update lock carries a token and timestamp, is released only by its owner, and recovers dead owners or locks older than an hour. Automatic updates are opt-out, at most once per 24 hours per executable, cache-recorded, launched detached with a filtered environment and neutral working directory, and skipped for `start`, `dashboard`, `watchdog`, `monitor` and while any PID-registered supervisor is live; the guard is re-checked immediately before replacement. Compiled binaries are release-marked only by `bun run build:release`, which the release workflow now uses; dotenv and `bunfig` autoload are disabled at compile time so a repository cannot redirect the updater. Supervisors register their PID for the updater and remove the registration on exit.

Unit tests cover tag/version ordering, asset naming, checksum/header/size rejection, metadata caps, atomic replacement, mode preservation, stale staging cleanup, staged-binary preflight, cache interval and target keys, lock contention/expiry/recovery, supervisor registration, guard re-checks, disabled environments, credential scoping and scheduling decisions. The compiled acceptance copies a release binary and proves `--check` only reports, `update` replaces the executable and reports the new `--version`, a plain project command triggers the real detached updater with a hostile `.env` present, and the environment marker is required.

Detached-process, registry and hostile-`.env` evidence uses a local release server and locally compiled payloads. The published-release path was exercised on macOS arm64 against real GitHub releases. First, a source run installed `v0.2.0` into a scratch path, proving metadata resolution, storage redirects, checksum verification, Mach-O header, staged `--version` preflight and atomic replacement. Then the published `v0.3.0` binary—itself produced by the updated Release workflow and therefore release-marked—reported `available` for `v0.4.0` and completed a live upgrade: it replaced itself with the published `v0.4.0` asset, reported `0.4.0`, reported `current` afterwards, and carried the new `update` command. The same flow was repeated inside a `linux/amd64` Debian container on an arm64 host against the published `linux-x86_64` assets: `install.sh --version v0.3.0` completed its checksum and staged preflight, `update --check` reported `0.4.0` available, `update` replaced the binary, `--version` reported `0.4.0`, and the follow-up check reported `current`. That run exercised the `uname -m` mapping, ELF header acceptance and CPU emulation, so the Linux path is now observed too. A later published release still has to be validated by its own users, published Linux assets are x86_64 only, and os/arch pairs without assets are unsupported. Registration is best effort and PID-based: a reused PID postpones automatic replacement, and a supervisor that starts between registration and the updater's final re-check is a residual race. A running process keeps its old binary, and its later CLI child invocations see the updated file. Releases remain unsigned and unnotarized, so verification trusts TLS and GitHub release storage; Linux glibc assets are not verified on musl/Alpine; Windows, downgrades and sticky pins are unsupported.
