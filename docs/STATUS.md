## CLI installation and self-update

`install.sh` and `crewplane update` share one release contract: a platform asset plus a sibling `.sha256`. The installer accepts `--version`, `--dir`/`--prefix` (both `VALUE` and `=VALUE` forms), `--dry-run` and `--help`, normalizes `uname -m` to the published asset names, retries transient downloads, enforces `https` for custom sources, stages inside the target directory, verifies the checksum and the staged binary's reported version, and renames atomically. It refuses unwritable directories instead of escalating to sudo, handles signals explicitly, and reports upgrades, PATH hints, shadows and non-sticky pins. Source tests execute the real script against a local fake release server for install, upgrade, pinning, argument forms, spaces in paths, CRLF and foreign-name checksums, mismatch, missing asset, failed lookup, unwritable directory, dry-run, bad arguments and staged-file cleanup.

`crewplane update`, `--check` and `--force` verify the published SHA-256, the executable header and the staged binary's `--version` before an atomic same-directory rename, preserving the existing mode and refusing symlinks, non-files, foreign owners and unwritable directories. Failures print a JSON outcome and exit non-zero. Release metadata and assets are read with streamed size caps; API requests accept only `https` (loopback excepted) and send credentials solely to `https://api.github.com`. The update lock carries a token and timestamp, is released only by its owner, and recovers dead owners or locks older than an hour. Automatic updates are opt-out, at most once per 24 hours per executable, cache-recorded, launched detached with a filtered environment and neutral working directory, and skipped for `start`, `dashboard`, `watchdog`, `monitor` and while any PID-registered supervisor is live; the guard is re-checked immediately before replacement. Compiled binaries are release-marked only by `bun run build:release`, which the release workflow now uses; dotenv and `bunfig` autoload are disabled at compile time so a repository cannot redirect the updater. Supervisors register their PID for the updater and remove the registration on exit.

Unit tests cover tag/version ordering, asset naming, checksum/header/size rejection, metadata caps, atomic replacement, mode preservation, stale staging cleanup, staged-binary preflight, cache interval and target keys, lock contention/expiry/recovery, supervisor registration, guard re-checks, disabled environments, credential scoping and scheduling decisions. The compiled acceptance copies a release binary and proves `--check` only reports, `update` replaces the executable and reports the new `--version`, a plain project command triggers the real detached updater with a hostile `.env` present, and the environment marker is required.

Detached-process, registry and hostile-`.env` evidence uses a local release server and locally compiled payloads. The published-release path was exercised on macOS arm64 against real GitHub releases. First, a source run installed `v0.2.0` into a scratch path, proving metadata resolution, storage redirects, checksum verification, Mach-O header, staged `--version` preflight and atomic replacement. Then the published `v0.3.0` binary—itself produced by the updated Release workflow and therefore release-marked—reported `available` for `v0.4.0` and completed a live upgrade: it replaced itself with the published `v0.4.0` asset, reported `0.4.0`, reported `current` afterwards, and carried the new `update` command. The same flow was repeated inside a `linux/amd64` Debian container on an arm64 host against the published `linux-x86_64` assets: `install.sh --version v0.3.0` completed its checksum and staged preflight, `update --check` reported `0.4.0` available, `update` replaced the binary, `--version` reported `0.4.0`, and the follow-up check reported `current`. That run exercised the `uname -m` mapping, ELF header acceptance and CPU emulation, so the Linux path is now observed too. A later published release still has to be validated by its own users, published Linux assets are x86_64 only, and os/arch pairs without assets are unsupported. Registration is best effort and PID-based: a reused PID postpones automatic replacement, and a supervisor that starts between registration and the updater's final re-check is a residual race. A running process keeps its old binary, and its later CLI child invocations see the updated file. Release signing (Ed25519, `release-keys.json`, `scripts/sign-release.ts`) is implemented in the updater, installer and release workflow but is enforced only once an operator adds a public key and the `RELEASE_SIGNING_KEY` secret; until then verification trusts TLS and GitHub release storage via the same-origin SHA-256, and releases are unnotarized. The workflow no longer overwrites published assets (no `--clobber`), though anyone with contents write access can still delete and re-upload them, so GitHub's immutable releases setting is also recommended; signatures do not prevent rollback or freeze to an older signed release (no signed metadata yet); `signedSince` lets older tags stay on SHA-256; Linux glibc assets are not verified on musl/Alpine; Windows, downgrades and sticky pins are unsupported.

## SEC-1 control directory relocation

The supervisor control plane moved from `<store>/supervisor` (inside roots harnesses may write; Codex is given `--add-dir <root>`) to a private per-user directory derived from the canonical primary root (`$CREWPLANE_STATE_DIR`, else `$XDG_STATE_HOME`, else `~/.local/state`, then `crewplane/projects/<key>`), created 0700 and verified on every use. Children are given the board location only. Pre-existing in-store state fails every project command closed until `crewplane migrate`, which refuses while a process you own is live, stages the legacy tree as fresh private copies and prints its complete configuration and a digest (adopted only with `--accept-config <digest>`), re-arms narrowing pending commands and quarantines widening ones. This is defense in depth: without an OS sandbox a same-user agent can still reach any file the user can, so it protects against directory-scoped harness sandboxes and accidental prompt-injected writes, not against deliberate same-user attacks. A deliberately planted legacy directory is handled by a strict allowlist and a digest-bound review (`migrate --dry-run`, then `--accept-config <digest>`), or set aside with `migrate --discard-legacy`, not by relocation alone: only the validated configuration, desired intent, a minimal state subset and narrowing commands are adopted, re-serialized, and everything else (leases, identity, sessions, logs, the watchdog tree, unknown files) is left behind. The review guarantees that what is adopted is exactly what was shown; a malicious configuration is kept out only if the operator notices it in the printed values, and a same-user agent with no OS sandbox can still reach everything. Liveness claims in the legacy directory count only for a registered supervisor whose executable matches. An agent can still deny service by creating `<store>/supervisor`, which forces that step. The control directory is bound to the project by a store marker and an identity file, so a moved repository or a changed environment fails closed instead of starting fresh. Traces, evidence and monitor output remain board state. `tests/lifecycle-binary.ts` was updated for the new location and its first two scenarios were exercised locally; the full script times out in the development sandbox and needs a normal host run.

Limits:

- The pty tests need `python3` with the `pty` module (present on ubuntu-latest and macos-latest runners); without it they skip with a logged reason, and nothing else covers the real-terminal path. They were run on Linux only; macOS pty behavior (EIO versus end of file on the master, controlling-terminal setup) is handled in `tests/pty-driver.py` but not verified here. - Each template uses one harness per role group: coordinator, implementers and reviewers. The wizard's `custom` choice picks one harness per group, not per lane.
- `confirmedStoppedAt` is an operator assertion. Setup refuses to record it when the control state says running or the shared liveness oracle reports a live supervisor (and `--install` rechecks under the install lock), but it cannot prove that unrelated harness processes are stopped; liveness evidence can be stale or missing.
- Binaries are checked as absolute, executable regular files that users outside your own groups cannot replace: the path is walked component by component (through every symlink and `..`), every symlink and the file must be owned by the current user or root, the file not world-writable and not group-writable by a group the current user is not in, a sticky directory judged by ownership only (so `/tmp` and multi-user Nix `/nix/store` `1775 root:nixbld` pass), and every other directory on the walk (and its ancestors) not world-writable, not foreign-owned, and not group-writable by a group the current user is not in (an injectable `{uid, gid, groups}` identity and an injectable lstat/readlink layer drive the tests with synthetic stat results, so every foreign-owner, foreign-group, sticky, loop, hop-limit, `..` and `/proc` case runs without root; the real-file-system tests remain as an integration layer). See docs/USAGE.md "Binary safety checks"; `doctor` applies the same check to each lane's effective binary and the top-level `binary` after its probes pass and reports `BINARY_UNSAFE` (exit 2); the check lives in `src/binary-safety.ts`, shared by setup and doctor. ACLs, mounts, attributes and capabilities are not examined, check-to-use races remain, versions, credentials and provider behavior are not checked, there is a window between checking and use, and no live harness run is claimed. The ownership rule only compares against the current user and root. The real-file-system foreign-owner tests run as root with `chown` to uid 65534 and are skipped where chown is not permitted; their synthetic equivalents are never skipped.
- `--out` is atomic and never overwrites, but it relies on hard links in the target directory. On a filesystem without them the write is refused. If an install succeeds and the later file publish fails, the configuration stays installed and the error says so.
- Harness-switch epochs compare only against the latest record per lane (as the supervisor's `assertSwitch` does) and use the installed config only for a lane with no record; Pi lanes follow the same rule. The supervisor can still refuse a switch when the lane is not drained. A Pi lane whose latest record has no epoch gets the run's fresh epoch without a note.
- `--out` git checks run git with fsmonitor and hooks disabled and refuse on any git failure other than a genuine "not a git repository" with no `.git` above; a git timeout (10 s) refuses. A SIGINT/SIGTERM/exit before publishing removes the hidden temporary file; SIGKILL or power loss can still leave it, and the next `--out` to the same target sweeps it once it is older than one hour (exact `.NAME.<12 hex>.tmp` name for the same target in the same directory, regular file by lstat, owned by the current user, mode 0600, one link, mtime and ctime older than the age; anything else, a younger file and any sweep error are ignored; never run for a refused path). Until such a run it stays on disk; there is no sweep at any other time.
