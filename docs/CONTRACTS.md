# Extraction interfaces v1

`src/contracts.ts` owns supervisor configuration, native run records, loaded state and actionable work identities. `src/project.ts` owns project discovery and policy validation. `src/ports.ts` defines the harness adapter seam and the `PlanParser` port (`(plan, existingIds) => PlannedCard[]`). Roadmap formats live in the `src/profiles/` registry (`planParsers`); core modules never import it, `roadmapFormat` is validated by shape in `project.ts`, and the composition root `src/board.ts` wires the registry into the read model and rejects an unregistered format with a clear error. The existing `lanes` configuration key is retained for compatibility, but IDs are configurable agents, not fixed names.

`src/engine/read-model.ts` composes durable task/claim/status/acceptance/message records with separately qualified runtime observations. Supervisor and HTTP share this projection, including pure display helpers; graph validation degrades to an explicitly unavailable graph instead of blocking board reads. No HTTP server is imported by the scheduler. HTTP and CLI are adapters over the same coordination services.

Control-plane location. The supervisor control plane (`config.json`, `state.json`, `desired.json`, the `commands/` queue, supervisor and watchdog leases, run logs, native session files and watchdog state/notices) lives in a private per-user directory outside the project, `<CREWPLANE_STATE_DIR | XDG_STATE_HOME | ~/.local/state>/crewplane/projects/<first 24 hex of sha256(realpath(primary root))>`, created 0700 and verified (owner, not a symlink, not group/world writable) before every use. The project store holds only the board: tasks, messages, assignments, claims, status, evidence, operational traces (supervisor-written telemetry that no control decision consumes) and monitor output (observation only). Children receive `CREWPLANE_COORD_DIR=<store>` and never the control path; the board CLI derives the control directory read-only for its execution guards. This is defense in depth against harnesses that enforce directory-scoped writes and accidental prompt-injected writes, not an authorization boundary against a same-user process without an OS sandbox. A pre-relocation `<store>/supervisor` is never silently ignored: every project command fails closed with one stable line until the explicit, liveness-checked `crewplane migrate` moves it; only an allowlist of the legacy tree is adopted (the validated configuration, `desired.json`, a minimal structural subset of `state.json` and re-armable narrowing commands), each file re-serialized from validated values; leases, identity, native sessions, run logs, the watchdog tree and anything unknown stay behind in the retired legacy directory; reads are bounded and non-blocking; the dry run prints everything adoptable and a digest of exactly the published bytes, and adoption requires `--accept-config <digest>` whenever anything is adoptable; widening commands are listed and never published, so they can never lift a hold implicitly. The halting verbs `status`, `stop`, `pause` and `cancel` remain available: a live new supervisor always wins, a credibly live old one is addressed in its legacy directory, and ambiguous legacy liveness queues narrowing verbs in both directories. A store marker and a control-side identity file bind the two, so a moved repository, a different environment or a re-clone fails closed. Under `CREWPLANE_HEADLESS_LANE` only `agents`, `task list`, `agent list`, `evidence`, `monitor`, `status` and `doctor` run.

File-store protocol v1 has a Crewplane namespace and canonical Git common-directory identity. Task records have independent assignment, scope, scheduling metadata, exclusive claim, reported status and integration acceptance. Messages are append-only UUID records with sender, recipient, kind, task, reply identity and optional exact review SHA. State writes use temporary files and rename; exclusive records use exclusive creation/link. Board mutation locks serialize scope/assignment/claim/status transitions. Board locks record PID/token ownership and recover only verifiably dead holders; live/unknown ownership stays protected. Process liveness (`src/liveness.ts`) is a signal-0 probe: only ESRCH is dead; EPERM and every other failure are unknown, never alive. Safety checks refuse unless the owner is proven dead, the watchdog reports unknown as `supervisor-unknown`, and the dashboard shows such a lane as stale. Lease and writer refusals on an unknown probe name the errno code (for example `Watchdog lease unavailable (EPERM)`), never a path. Legacy directory locks and invalid lock metadata require manual inspection; do not auto-delete them. Store files are private local-user coordination, not a hostile multiuser authorization boundary. Private state and evidence files are read through shared helpers that open without following a final symlink or blocking on a FIFO and require a regular file, no group/other mode bits, a size cap (64 KiB for watchdog state) and, on POSIX, ownership by the current user; a store restored or copied as another user, including root, is rejected until its ownership is repaired. Ownership is not checked where `getuid` does not exist (Windows). The control-plane readers in `src/control.ts` and `src/migrate.ts` are deliberately separate: they apply their own size caps and non-blocking opens, and migration decides liveness with its credible-supervisor oracle, using the shared probe only where a plain pid-exists check is meant (EPERM maps to foreign).

FAIR-V1 consumes explicit candidates, dependencies, role identity, active work, budgets and holds and returns reasons for selected/blocked/capacity states. The model does not choose executable eligibility. Phase gating is explicit coordinator authorization; task prose does not become authority.

Harness adapters (Codex, no-tools Pi, Claude Code and OpenCode) consume native stream events into bounded session/model/usage/final-result observations and declare resume, native-versus-prompted structured result, tool policy, observed model/cwd and partial usage explicitly. Lane configuration also declares optional guidance (`instructionsPath`), per-lane run-rate/time limits, a Claude per-invocation cost cap, Claude MCP/settings/tool isolation, an OpenCode agent profile and reported-cost/denial observations. No-tools harnesses are reviewer-only: their prompt inlines bounded JSON-encoded policy and the pinned task card, and each turn ends as a paused advisory decision with consumed events rather than board completion. Session identity is harness-specific: a UUID for Codex, Pi and Claude Code, and `ses_` plus alphanumerics for OpenCode. Cross-harness, cross-epoch and malformed identities are rejected. An audited `retry --new-session` clears exactly one native session after atomic ownership, hold and harness/epoch checks and records an applied/refused control outcome. A final state is one of working/waiting/ready/needs_operator, with a bounded summary. Schema versions and session identity remain explicit. Completion and trace settlement are part of process ownership.

Operational trace, usage and evidence modules retain versioned records and capacity limits. Logical evidence route aliases replace Relay's product-specific path whitelist. Usage coverage distinguishes unknown dimensions from measured values; the detailed ledger is not yet connected to all runtime providers.

Breaking persisted or command meanings require a new version and an explicit migration. No automatic Relay store migration is provided. New harnesses must supply capability and lifecycle fixtures before registration. Keep public interfaces centralized; do not redefine task or process entities in the dashboard.

Project policy v2 adds optional exact requiredVersion and per-agent ordered promptFiles. Older policy v1 remains supported but cannot declare these fields. Version mismatch fails before project store preparation and a configured pin disables project-command automatic update scheduling. The pin is decoded before role and schema-version validation so a project owned by a newer release still names the pin. The mismatch message stays a single line because the supervisor persists it as a pause reason; recovery context (pin path, running binary, direction, docs pointer) is rendered by the CLI only and never includes an executable install command, since lanes read CLI stderr and a repository controls its own pin. The control verbs stop, pause, resume, cancel and resolve stay queueable under a mismatch so an operator can halt, cancel or answer live work, and the pin command runs because repointing a stale pin is the case it exists for; every other project command remains blocked. The pin command may only target the running release: it cannot install a release, cannot pin to a different version, refuses while a supervisor runs or without --confirm true, and rewrites nothing when the pin already matches. Supervisors record their release as an optional supervisorVersion in their state so a mismatched CLI can name the release that will interpret a queued verb and warn that it may be ignored; the field is absent for supervisors older than the recording, which the CLI reports rather than guessing. Self-update retains the release it replaces as `<releasesRoot>/<version>/crewplane` (root: an absolute CREWPLANE_RELEASES_DIR, else XDG_DATA_HOME/crewplane, else ~/.local/share/crewplane), verifies the retained copy before trusting it, and refuses the swap when it cannot retain. A pin mismatch dispatches to that copy only when the copy and its release directory are this user's, are not symlinks and are not group/world writable, and the copy reports exactly the pinned version; dispatch is one hop per release, never runs for `pin`, and is skipped while a live newer supervisorVersion owns the store or the recorded state is unusable. Prompt rendering uses bounded canonical-primary files, preserving built-in reviewer/visual role boundaries. Store/native configuration protocols remain unchanged; these fields never authorize execution or migrate private state.

Operator controls are a versioned command protocol stored in the control directory: scoped (instance/lane/task/run), generation- and revision-bound, applied serially by the supervisor, and recorded with exactly one outcome and a bounded audit log. Narrowing controls (holds, drain, cancel) are safe to apply late; widening controls (release, retry, cleanup acknowledgement, new-session, resolve) must match the observed generation, revision, run or session. Controls never lift holds implicitly, signal a process that is not a live child of the current generation, clear an unobserved failure, raise budgets, write board state, or release ownership before completion is persisted. State v2 adds instance holds, lane revisions, control sequence/log and decision pause ids while remaining backward-readable from v1. Dashboard mutations, when explicitly enabled, expose only hold and cancel behind Origin, token and JSON checks; the default dashboard remains read-only.

## CLI output contract

The CLI is both an operator interface and a scripting surface. These rules
describe what a consumer may rely on today. `--help` is the enumerated command
and flag list, and `src/help.test.ts` asserts that every control form printed
there is accepted by the control policy.

**Streams.** stdout carries only the command's result. stderr carries
diagnostics, advisory warnings, banners and errors. A failing command writes
nothing to stdout, except `update` (which reports its failure as a JSON
document) and a `--wait` control, whose outcome is the result.

**Human-only output.** `--help`, `--version`, the `agents` usage text,
`agents prompt` and the `dashboard` startup banner are prose on stdout. Every
other successful command writes JSON. `monitor` is the exception: it writes a
prose startup banner and then one compact JSON object per observation.

**Reports.** A report is an object pretty-printed with two spaces and exactly
one trailing newline; two legacy commands still print a bare array
(`agents inbox`) or a bare `null` (`watchdog status`). `null` means unknown or
not applicable, `[]` means known empty, and `0` is a measured value. Fields
named `reason`, `detail`, `label` or `text` may contain prose; enum-like fields
use closed values. Key order is construction order and is not a contract; array
order is (tasks and messages are sorted, lanes follow configuration order).

**Exit codes.** `0` success, including a queued control without `--wait` and an
`applied` or `noop` `--wait` outcome; `1` operational failure, invalid local
input, unconfigured project (except `doctor`, see below) or release-pin
mismatch; `2` a supervisor
`refused` or `invalid` outcome under `--wait`, or, for `doctor`, a diagnosed
problem (the JSON report is still printed to stdout). The meaning of `2` depends
on the command; `doctor` on an unconfigured project exits `2` with
`CONFIG_MISSING` (it used to exit `0`); `3` a `stale` outcome under
`--wait`; `124` a `--wait` timeout, where the command remains queued and may
still apply.

**Doctor.** `doctor` never aborts on a failed check: each failure becomes an
entry in `problems` (`{code, lane?, message}`), `ok` is `problems.length === 0`,
and the exit code is `0` when `ok` and `2` otherwise, with the report on stdout
either way. `message` is a fixed validation message, never raw engine text.
`code` is a closed set: `CONFIG_MISSING` (not configured), `CONFIG_INVALID`
(unreadable or invalid configuration, or a lane that is not a plain object or
names an unsupported harness), `BINARY_MISSING` (no binary configured, or the
path does not exist), `BINARY_INVALID` (not a string, relative, or not a regular
file), `BINARY_NOT_EXECUTABLE`, `BINARY_UNSAFE` (a binary that passed the probes but that users outside the current user's groups could replace, or whose path they could redirect, by the rules in docs/USAGE.md "Binary safety checks"; `lane` when a lane's binary; change note: scripts gating on `doctor`'s exit code can now see exit `2` for an existing configuration whose binary is replaceable by other users, which `configure` and `start` still accept), `INSTRUCTIONS_INVALID` (a lane's instruction
file), `RELEASES_ROOT_INVALID` (relative `CREWPLANE_RELEASES_DIR` or
`XDG_DATA_HOME`) `CACHE_DIR_INVALID` (relative `CREWPLANE_CACHE_DIR`) and `LEGACY_LAYOUT` (a pre-relocation `<store>/supervisor` holding state; doctor stays exempt from the migration gate but reports it and exits 2).
Configuration is validated without the binary-existence check, so a missing
binary never hides another configuration error; binaries are reported only by
the probes, and `config` is `valid` when only binaries fail. Each lane's
effective binary is the harness's `binaries` entry, or the top-level `binary`
for Codex; it is probed (absolute, regular file, executable by the current user) and, when that passes, safety-checked, and never executed. The executability check is POSIX-only: on Windows `X_OK`
behaves like `F_OK`, so `.cmd`/`.ps1` shims count as regular files. Lane
`binary` is `{path, ok, problem?}`. Top-level `defaultBinary` probes the
configuration's top-level `binary` itself (same shape, or `null` when unset),
independent of `binaries.codex`; its failure is reported without a `lane`
unless a lane already reported the same path. `warnings` has the same shape but
never affects `ok` or the exit code: `INSTRUCTIONS_GLOBAL_UNAVAILABLE` reports
a missing or unusable global instructions file. `config` is `valid`, `invalid`
or `not-configured`; `runtime` is `compiled` for a standalone executable and
`bun` otherwise. Credentials and provider operation are not probed. The configuration, lane and binary checks live in `src/doctor-config.ts` and are shared with the dashboard's `GET /api/config`. Pin
mismatches, unsafe stores and a non-repository or missing `git` are refused
before `doctor` runs, as for any project command (exit 1, nothing on stdout).

**Setup.** `setup` prints one report object on stdout on success: `version` (1), `mode` (`interactive` or `non-interactive`), `template` (`codex`, `claude`, `opencode`, `mixed`, or `custom` in the wizard), `config` (the runtime JSON `configure --file` accepts, without `root` or roles), `confirmedStopped` (boolean), `written` (absolute `--out` path or `null`), `installed` (boolean), `problems` (`{code, lane?, message}` entries, empty when valid), `notes` (strings) and `next` (suggested commands). Prompts, echoes, notes and problem lines go to stderr. Exit `0` is a valid report with no problems; `2` prints the report with `problems` and writes or installs nothing (the final verification found a binary or instruction file unusable or unsafe after the answers were accepted, for example a binary replaced or removed during a wizard review, reported as `BINARY_INVALID` or `BINARY_MISSING`); `1` prints nothing on stdout (including a missing `--tasks`, a refused stop confirmation, `--out` or install, and an unsafe binary). `--out` is published atomically and, with `--install`, only after the install succeeded. `notes` also carry binary rejections (setup records only binaries that users outside your own groups cannot replace, nor any directory or link on their path; ACLs, mounts, attributes, capabilities and check-to-use races are not covered; `doctor` applies the same check and reports `BINARY_UNSAFE`) and, in non-interactive runs, harness-switch and discarded-`sessionEpoch` notices (the wizard prints those once before its review prompt instead of repeating them in `notes`); lanes that switch harness carry a generated `sessionEpoch` in `config`. Interactive mode requires stdin and stdout to be terminals, so its report is never redirected. Full flag and exit-code rules are in docs/USAGE.md "Guided setup".

**Errors.** Errors go to stderr, never stdout. The first line is
`crewplane: MESSAGE`; continuation lines are indented and carry recovery
context. The release-pin message stays one line because the supervisor persists
it as a lane pause reason; the CLI-only recovery context never contains an
executable install command.

**Controls.** A control verb queues a private command file and prints
`{queued, id, activation}`; it never applies the control itself. With `--wait`,
the outcome document replaces that shape and `activation` is always `false`.
Boolean flags take an explicit `true`: the forms in `--help` are the accepted
grammar, not shorthand.

**Holds.** `agent list` and the dashboard report both lane-scoped `held` and the
instance-wide `instanceHeld` flag; a lane is paused when either applies.
`status.view` reports the same intent per lane.

**Privacy.** Reports are explicit projections. `status` is the documented
exception: it includes the raw persisted `state` alongside `view` so an
operator can inspect recovery evidence. Agent-authored text is data, never
instruction.

**Deferred to output schema v1 (breaking; do not treat as stable).** Report
version markers are inconsistent (`version: 1`, `schemaVersion: 1`, or none),
and `status` carries none. `agents inbox` returns a bare array and
`watchdog status` a bare `null`. `monitor --status` and the `monitor` event
stream use different keys for the same fields. `pin` omits `next` when nothing
changed. Usage and precondition failures exit `1` rather than dedicated codes,
so scripts cannot separate "bad flag" from "not configured" or "wrong release".
Several always-false fields (`activation`, `started`, `servicesStarted`,
`init.running`) are reported as if they were observations. `agent list` exposes
prose in `configState` and `harness`, which the dashboard parses.

## Dashboard HTTP API

The dashboard serves public embedded assets and a set of data routes under `/api/`. Rules shared by every data route:

- **Auth.** A per-launch session token in the `x-crewplane-session` header is required on every `/api/*` request when the dashboard is launched by `crewplane dashboard`; without a matching header the answer is `401 {"error":"Session missing or expired. ..."}`. A token in the query string or any other header is never accepted. Host must be exactly `127.0.0.1:PORT` and a present `Origin` must be `http://127.0.0.1:PORT`, otherwise `403`. The Host/Origin check runs first.
- **Method.** Data routes accept `GET` only (`405` otherwise). The single write is the opt-in `POST /api/control` (below and docs/USAGE.md "Dashboard controls").
- **Errors.** `400` for unknown, repeated, malformed or out-of-range parameters (the body never echoes the offending value), `503 {"error": ...}` when the board cannot be read, `404` for unknown paths. Every response sends `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and the strict CSP.
- **Data.** Responses are explicit allowlisted projections. They never contain environment values, tokens, file contents, raw provider payloads or private reasoning. Persisted strings are stripped of control characters and length-bounded; clients still render them with `textContent` only. `null` means unknown or not applicable and is never `0`.

Existing routes are unchanged (the snapshot gained one additive field, `graphModels`, below): `GET /api/snapshot`, `GET /api/runs[?task&lane&harness&before&limit]`, `GET /api/runs/:runId[?after&limit]`.

### Snapshot `graphModels` (additive)

`graphs.{dependencies,communication}` keep their shape and the 50 node and 100 edge display cap. Beside them the snapshot carries `graphModels.{dependencies,communication}`, the same explicit relationships without that cap, in a compact form for the page's clusters, focus and paging: `nodes` (up to 1,100; null fields omitted; tasks add `phase` and `owner` grouping hints), `edges` (up to 3,000 tuples `[from, to, kindIndex, label, threadId, at, unanswered]`, `kindIndex` into `dependency`, `awaiting-answer`, `review-handoff`, `message`), `hidden` and `truncated` (what the model itself left out). It is absent when the graph is unavailable. It grants no authority and the page still draws at most 50 nodes and 100 edges at a time.

### `GET /api/events` (server-sent events)

`Content-Type: text/event-stream`, no parameters. Because `EventSource` cannot send the session header, clients read it with `fetch()` and a `ReadableStream`. Frames:

| Frame                                                                                                      | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `retry: 3000`                                                                                              | Reconnect hint, sent first.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `event: ping` / `data: {"at": ISO\|null, "id": string\|null, "kind": "snapshot"\|"error"\|"resync"\|null}` | Sent on connect and every 15s. `at` is when the board was last **read successfully** (never the time the ping was sent), so a stuck or failing read cannot make stale data look current; `id` and `kind` name the event that is current. All three are `null` until the server holds a read made while a client was connected (a fresh connect after an idle period).                                                                                                                                                                                                                                                 |
| `id: <boot>-<n>` / `event: snapshot` / `data: <the /api/snapshot body>`                                    | The board changed. Sent once on connect and then only when the serialized snapshot content (excluding `updatedAt`) changes, and only when the serialized body is at most `MAX_EVENT_BYTES` (below). The body is the newest read of that content: a later read with the same content keeps the event id but replaces the cached body, so its `updatedAt` is never older than a client that already holds a newer polled snapshot. A client ignores a pushed snapshot whose `updatedAt` is earlier than the one it already shows (and a heartbeat `at` earlier than what it shows), so "Checked" never moves backwards. |
| `event: resync` / `data: {"reason":"snapshot-too-large","limitBytes":N}`                                   | The board is too large to push. No `id`, no snapshot. Sent once per episode (not on every change while it stays too large) and to a client that connects during one. The client stays on the stream and keeps polling `/api/snapshot`; the next snapshot that fits is pushed with a new id.                                                                                                                                                                                                                                                                                                                           |
| `id: ...` / `event: error` / `data: {"error": <the /api/snapshot 503 message>}`                            | The board is unreadable. Sent once per failure episode; the stream stays open and the next readable snapshot is always re-sent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

**Size limit.** `MAX_EVENT_BYTES` is 8 MiB (`src/engine/dashboard/live.ts`): the largest serialized `snapshot` body the stream will carry. The client's parser limit (`MAX_EVENT_CHARS`, `app/live-core.js`) is 8 MiB plus 64 KiB and a unit test keeps it above the server's, so a valid event can never trip it. `snapshot.messages` is the whole board's message list and has no retention or pagination bound, so a board with roughly 20,000 or more messages (about 400 bytes each) exceeds the limit. The dashboard still works there by polling `/api/snapshot`, which has no size cap, and the indicator says `polling`. Bounding the list would change `/api/snapshot` itself and is not done here.

Limits: one shared computation per server, never overlapping, only while at least one client is connected and none otherwise. It runs every 1s at best; after each computation the next one waits `max(1s, 5 x how long the last one took)`, at most 30s, so a slow board is read less often rather than back to back. There is no sound cheap change signal to skip a read with (board content lives in task cards, the coordination store and git state, and directory mtimes miss in-place edits), so the interval is the only adaptation. A computation that spans the last client leaving is discarded and repeated, so a client that connects later is never sent a cached snapshot from before the last client left; it waits for a read that began while a client was connected, and a reconnecting client that is already current is told so by a ping. At most 8 clients, a ninth gets `503 {"error": ...}` with `Retry-After: 5`. A client that is merely behind receives only the latest event (updates are coalesced, never queued), so at most one event (`MAX_EVENT_BYTES` plus framing) is ever unflushed per client. The per-client unflushed-bytes limit (default 16 MiB, twice the largest event) is checked before and after every write and closes the client when exceeded, which in practice only happens if a single frame outgrows it; a client that cannot accept writes for 10s is closed. `Last-Event-ID` equal to the current event id suppresses the redundant initial snapshot; an unknown or malformed id is ignored; a `resync` carries no id so a reconnect never presents it as progress. Event ids are scoped to one server launch. The stream carries snapshot changes only; run traces keep polling `/api/runs/:runId`. Closing the server ends every stream and clears every timer.

Client rules (`app/live.js`, `app/live-core.js`): the transport is `live` only once a snapshot was applied (or a ping naming the already-applied snapshot arrives), never because a stream opened; `resync` means `polling` without reconnecting. The reconnect backoff counter (1s doubling to 60s, +-25% jitter) resets only after a snapshot was rendered or the stream stayed up 30s, never on connect or ping, and an immediate catch-up poll after a drop happens only for a stream that was up 30s. A snapshot that fails to render is not remembered as received (the next connection sends no `Last-Event-ID`), keeps the banner, drops to polling and is retried with backoff; pings do not clear it. A poll that started before a pushed snapshot was applied is discarded. A tab hidden for 30s closes its stream (the slots are scarce) and reopens it, with an immediate refresh, when shown again; while live, returning to a visible tab does not poll.

### `GET /api/config`

No parameters (`400` otherwise). Built by the same inspection as `crewplane doctor` (`src/doctor-config.ts`), so problem codes, messages and per-binary results cannot drift; a parity test compares them for the same project. Update-cache and releases-directory problems (`CACHE_DIR_INVALID`, `RELEASES_ROOT_INVALID`) belong to the CLI environment and are not reported.

Shape: `version` (1), `installed` (config.json readable), `state` (`valid` | `invalid` | `not-configured`), `digest` (the scheduling fingerprint of the installed config: SHA-256 of its key-sorted JSON, or `null`), `loadedDigest` and `digestsMatch` (against the running supervisor's loaded fingerprint, `null` when unknown), `ok`, `problems` (`{code, lane|null, message}` in doctor order, same closed code set including `CONFIG_MISSING`, `CONFIG_INVALID`, `BINARY_*` incl. `BINARY_UNSAFE`, `INSTRUCTIONS_INVALID`, `LEGACY_LAYOUT`), `warnings` (`INSTRUCTIONS_GLOBAL_UNAVAILABLE`, `DIGEST_UNAVAILABLE`), `problemsTruncated`, `legacyLayout`, `roles` (`{coordinator, reviewers, stale}`; `stale` is true when the installed roles differ from committed project policy), `budgets` (`{effectiveFrom: "configured", configured, loaded, reloadPending}`: `configured` and `loaded` are each `{maxParallel, maxRunsPerHour, maxRunMinutes, intervalSeconds}` or `null`, from the installed configuration and from what the running supervisor loaded; `reloadPending` is `true` when the loaded fingerprint differs from the installed one, `null` when either is unknown. Every lane's effective cap is computed from `configured` alone, so a lane's own value and the default it falls back to can never come from two configurations; the supervisor does not persist per-lane loaded caps, so the loaded values are shown beside, not mixed in. A lane's `maxRunsPerHour` is a per-lane cap, and the global one is the default for a lane without its own), `lanes` (at most 64, then `lanesTruncated` is `true`: `id`, `enabled`, `valid`, `role` `coordinator|reviewer|implementer`, `reviewerRole`, `harness`, `model`, `permissions`, `capabilities`, `instructions {configured, status: none|ok|invalid}` (never the path), `budgets {maxRunsPerHour, maxRunMinutes, maxCostUsdPerRun, effectiveMaxRunsPerHour, effectiveMaxRunMinutes}` (each a non-negative number or `null`; a value of any other shape reads `null`), `passEnv` (variable names only, at most 64, names that are not plain identifiers are dropped), `binary {path, ok, code, problem}`, `claude`, `opencode`), `binaries` (one per harness in use plus `default`: `{harness, path, ok, code, problem}`), `credentials: "not-probed"` and `binariesExecuted: false`.

Malformed configurations (an `allowedTasks` that is not a list, `reviewers` that is a string, `lanes` that is not an object, lane entries that are not objects, a document that is not an object) never fail the route: doctor's problem for it is returned with the same code and message, role fields that cannot be read fall back to the defaults, and `digest` is `null` with a `DIGEST_UNAVAILABLE` warning when the configuration cannot be fingerprinted. Nothing configured is copied through unsanitized: numbers must be non-negative numbers, `permissions` is one of the closed set (`no-tools`, `auto-approve`, `harness-configured`, `harness-controlled`, `permission-mode:<known mode>`, else `invalid`), `claude.mcp` and `claude.settingSources` are limited to their closed value sets, and free-text names (model, tool lists, agent) are control-stripped and length-bounded.

Bounds, which apply to this route only (`crewplane doctor` reads and inspects without them): at most 64 lanes are inspected and probed, at most 100 problems are returned (`problemsTruncated`), and `config.json` is read with the same symlink-refusing, size-capped reader as the other control files (1 MiB; a symlink or larger file reads as `CONFIG_INVALID`, which doctor, following symlinks, would not report). A lane that failed validation appears with `valid: false` and no harness data.

### `GET /api/control-log?limit=N&after=SEQ`

Projection of the supervisor's bounded audit log (`state.controlLog`, at most the latest 200 entries). `limit` is 1 to 200 (default 50); `after` is a sequence number (digits, at most 9). Without `after` the newest `limit` entries are returned; with it, the first `limit` entries newer than `after`. Entries are always ascending by `seq`. Response: `version`, `available` (state.json readable), `entries`, `latestSeq`, `retainedFrom`, `retained`, `retainedFromId` (the id of the oldest retained entry, or `null`), `afterId` (with `after`: the id of the entry at that sequence when it is still retained, else `null`), `hasMore` (only with `after`), `nextAfter` (pass it as `after` to continue). `retainedFromId` and `afterId` let a client holding a cursor tell a log that was reset and grew past that cursor (same sequence numbers, other ids) from one that only pruned its oldest entries; the dashboard then reads the log again from the start. It also re-reads when `latestSeq` is behind the cursor, when `retainedFrom` is more than one past the cursor (entries were lost unseen) or when `retainedFrom` is older than the oldest entry held.

Entry: `{id, seq, at, issuer, action, scope: instance|lane|task|run, target, lane, task, run, outcome: applied|noop|refused|stale|invalid, reason}`. `lane`/`task`/`run` repeat `target` for the matching scope and are otherwise `null`. `reason` is the supervisor's outcome code (for example `STALE_REVISION`), bounded to 96 characters. An unknown outcome reads `invalid`.

### `GET /api/controls`

No parameters (`400` otherwise); requires the read session like every `/api/*` read. Without `--controls true` it answers `{"version":1,"enabled":false}` and the page renders no controls. With controls it answers `{version, enabled: true, verbs, cliOnly: [{verb, reason}], supervisor {running, draining}, instanceHeld, stopAvailable, limits {maxNoteChars}, lanes}` where each lane is `{lane, rev, held, verbs, tasks}` and each task `{task, runId, sessionId, status, pauseKind, pauseId, cleanupUnverified, verbs}` (at most 100 lanes and 50 records per lane). `rev` is the lane revision a widening command must pin; `runId`, `sessionId` and `pauseId` are the other pins. `verbs` lists what is currently meaningful (`pause`, `resume`, `retry`, `nudge`; per record `resolve`, `cancel`, `retry-new-session`, `retry-confirm-cleanup`), derived from the same persisted state the supervisor decides from. It is **advisory**: the server and supervisor remain the authority. It never contains the controls token.

### `POST /api/control`

Enabled only by `crewplane dashboard --controls true`. Requires, each `403 Forbidden` (no detail) on failure: controls enabled, `Origin` exactly `http://127.0.0.1:PORT`, header `x-crewplane-token` equal to the per-launch controls token (distinct from the read session token, which alone is never enough), header `x-crewplane-session` equal to the per-launch read session whenever the server was started with one (always, for `crewplane dashboard`; it is the same gate every `/api/*` read has, and the page always sends both) and `Content-Type: application/json`. Body at most 4 KiB (`413`), valid JSON (`400 INVALID_JSON`). Fields: `action`, `lane`, `task`, `run`, `all`, `confirmCleanup`, `newSession`, `resolution`, `pauseId`, `text`, `expectRev`, `expectRun`, `expectSession`, `requestId`; any other field is `400 UNKNOWN_FIELD`. The server adds `issuer: "dashboard"`, `at` and the supervisor `generation`, and validates with the same `control()` as the CLI; it never applies a command, it only writes `commands/<requestId or new uuid>.json` through the same queueing function as the CLI (`src/engine/control-queue.ts`) after the CLI's legacy-layout gate: widening verbs while an in-store legacy supervisor directory exists are `409 LEGACY_LAYOUT`; `pause`, `stop` and `cancel` are written to the control directory and, as the CLI does, the legacy directory when it may hold a live older-release supervisor, each copy bound to that directory's own generation. `requestId` must be a lowercase UUID (8-4-4-4-12 hex).

Success: `200 {"queued": ACTION, "id", "status": "queued", "outcome": null, "afterSeq", "supervisor": "running"|"not-running", "warning"?, "legacy"?, "replay"?}`, where `supervisor` and `warning` describe the directories actually used (liveness is computed on every path, including a replay) and `legacy: true` marks a command also queued in, or only in, a legacy directory. `id` is the command id to find in `GET /api/control-log` (entries carry `id`; poll with `after=afterSeq`). `outcome` is always `null`: the single outcome (`applied|noop|refused|stale|invalid`) is recorded later by the supervisor, or the command is refused as stale if none runs.

Errors, each `{"error", "code"}`: `400` `INVALID_JSON`, `INVALID_CONTROL`, `UNKNOWN_FIELD`, `UNSUPPORTED_ACTION`, `CLI_ONLY` (`rollout`, `stop` with `cancelActive`, `resume` with `all`, `cancel` with `all`; `pause` with `all` is accepted), `PIN_REQUIRED` (widening verbs without `expectRev`; `retry` with `confirmCleanup` without `task` and `expectRun`; with `newSession` without `expectSession`), `NOTE_REQUIRED` (`nudge`, `resolve`, `retry` with `confirmCleanup` or `newSession`), `NOTE_TOO_LONG` (over 2000 characters), `REQUEST_ID_REQUIRED` (`nudge` and every widening verb), `UNKNOWN_AGENT` (the lane is not configured; narrowing verbs are checked only when a configuration is readable, as in the CLI); `409 REQUEST_ID_REUSED` or `409 LEGACY_LAYOUT`; `413`; `429 RATE_LIMITED` / `QUEUE_FULL` with `Retry-After` (never for `pause`, `stop` or `cancel`); `503` when the command cannot be queued.

Idempotency: `requestId` (a UUID) is the command file name. A repeat is answered with the original `id` and `replay: true` and queues nothing, from a ten-minute bounded memory (256 entries), from the exclusive create when another dashboard queued it, and from the supervisor's record of consumed ids. For a consumed id, a different verb or target than the control-log entry records is `409 REQUEST_ID_REUSED`; the log keeps no payload, so a consumed id with the same verb and target but a different note or pin, or one no longer in the log, replays by id alone. The supervisor unlinks any command file whose id is already in `state.commands` on every scan and at start. Rate limit: 20 queued commands per minute for `nudge` and the widening verbs, and at most 50 waiting widening/other files (pending halting files are not counted, so a flood of halts cannot make a recovery verb `QUEUE_FULL`; files that cannot be read as a command, and any beyond the first 1000, are counted); replays do not count. `pause`, `stop` and `cancel` are exempt (halting is never refused) and are deduplicated against a still-pending identical halt instead: identical means every field that matters (verb, agent, run, `all`, task, note, `expectRev`, `expectRun`, `expectSession` and, for `stop` and `cancel`, generation). Such a repeat is answered with the pending `id` and `replay: true` and adds no file, unless a pending command of a different kind on an overlapping scope (same agent, `all`, or instance-wide) would be consumed after the earlier file (pause --all, resume --all, pause --all queues the second pause), or the earlier file's id is already recorded as consumed. The check reads at most 1000 pending files and is not atomic with the later exclusive write, so two simultaneous identical requests can both queue (harmless: halting is idempotent). Disk used by halts is therefore bounded per distinct command, not globally: a holder of the controls token can still add files by varying the pins, run ids or generation (each a few hundred bytes); the files are removed as the supervisor consumes them, and when the configuration or legacy target cannot be resolved the lane check is skipped as in the CLI.

Revision pin: `laneRev[lane]` is incremented exactly when a record's status or pause kind in that lane actually changes (run start and finish, a failure pause the supervisor newly creates including at start and in checkout/setup validation) and when an applied control changes something in the lane (a hold, a release that released something, a retry, resolve or cancel request); re-asserting a state a record already has, such as the supervisor re-pausing a lane that is still blocked by retained process ownership on every scheduling pass, does not move it. No other event does; a widening command pinned to an older revision is recorded `stale`. It does not cover notes, usage counters, other lanes or the supervisor generation.

### `GET /api/usage`

No parameters (`400` otherwise). Uses only retained records; nothing is estimated. Token and cost figures are **reported counters and per-invocation observations, not billing totals**.

- `caps`: `{source: configured|loaded|null, perLaneDefault {maxRunsPerHour, maxRunMinutes}|null, loaded {maxRunsPerHour, maxRunMinutes}|null, loadedDiffers}`. Every cap in the response comes from one source: the installed configuration when readable, else (defaults only, no lane has its own cap then) what the running supervisor loaded. `perLaneDefault.maxRunsPerHour` is the configured cap that applies to **each** lane without its own; it is not a total across lanes. `loaded` is shown beside it, never mixed in; `loadedDiffers` compares only these two numbers (use `/api/config` `digestsMatch` for anything else).
- `total`: `runsLastHour`, `tokens {semantics, input, output}`, `series` (24 hourly buckets, oldest first, aligned to `window.bucketStarts`).
- `lanes[]` (at most 64): `runs {lastHour, cap, capSource: lane|default|null, remaining}`, `durations {maxRunMinutes, recent[] {task, startedAt, finishedAt, durationMs, status}, recordedRuns}` (latest run of each retained record, newest 10), `tokens {semantics, input, output, recordsReportingInput, recordsReportingOutput, retainedRecords}` (sum over retained records whose provider reported the dimension with a usable counter, else `null`; `recordsReporting*` counts exactly those records), `cost {semantics, maxCostUsdPerRun, recent[] {task, at, costUsd, overCap}, maxObservedUsd, anyOverCap}` (`overCap` is `null` without a configured cap), `series`.
- `coverage`: `counters` (source supervisor state records; terminal records are compacted away, so counters are not lifetime totals), `durations`, `series` (source operational traces: `retainedRuns`, `oldestRetainedAt`, `retentionLimited`, `incomplete`, `complete`) and `ledger {connected: false}`: the detailed usage ledger is not written by the runtime and is not read.
- A series bucket is `null` unless the trace store demonstrably existed for all of it: some retained run must have started before the bucket (strictly before when retention pruned older runs), and no page may have been missed. A new install, a store with no run yet, the bucket holding the oldest retained run, pruned history and an unreadable store all read `null`; a number, including a measured `0`, only for a covered bucket. So a project whose first run began 10 minutes ago reports no series data at all (its `runs.lastHour` still counts that run), and `coverage.series.complete` is true only when no bucket of the window is `null`.

### Evidence routes

All existing evidence routes keep their shape. Added:

- `GET /api/evidence[?task&run&limit&cursor]`: `run` (an opaque `qa_` id) narrows to that run in the same list shape (empty when absent or when `task` disagrees); `limit` is 1 to 20 (default 20) runs; `cursor` is the `nextCursor` of a previous page and must be a `qa_` run id (an `ev_` artifact id, a garbage value or a run id the store does not know is `400`, as on `/api/evidence/artifacts`; the store's refusal of a request is always `400`, only a failure to read is `503`). Unknown or repeated parameters are `400`.
- `GET /api/evidence/artifacts[?task&run&limit&cursor]`: flat artifact metadata for a gallery, newest run first, without content. `limit` 1 to 200 (default 100); `cursor` is an `ev_` artifact id (the previous `nextCursor`). Entry: `{id, kind: image|video, mime, size, createdAt, task, run, lane, testedCommit, sha256, route, scenario, step, browser, viewport, outcome, findingIds, recheckOf, url}`.
- `GET /api/evidence/artifacts/:artifactId` serves stored bytes with `Content-Type` from a four-value allowlist (`image/png`, `image/jpeg`, `image/webp`, `video/webm`; anything else is `application/octet-stream` as an `attachment`), `Content-Disposition` with a fixed filename, `Content-Length`, `Content-Security-Policy: default-src 'none'; sandbox`, `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: same-origin`. Because the route needs the session header, the gallery fetches artifacts and displays them from `blob:` URLs, so the page CSP is `img-src 'self' blob:; media-src 'self' blob:` (no other directive admits `blob:`). The client gives a blob the artifact's recorded type only when it is one of the four allowlisted values and equals the response `Content-Type`, and only when the declared `Content-Length` (when present; a missing one is not read as 0) and the number of bytes actually read both equal the artifact's recorded `size`, which must itself be within the 16 MiB viewing limit; any other type is download-only as `application/octet-stream`. This route's own `Content-Security-Policy: default-src 'none'; sandbox` is unchanged. See docs/dashboard-design.md (Evidence gallery and blob handling).
