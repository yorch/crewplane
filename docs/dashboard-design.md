# Dashboard design

The dashboard is a read-only operations cockpit (with opt-in operator controls, see "Operator controls") for one Crewplane project. The redesign changes presentation, navigation and client-side state only. HTTP routes, the shared read model, polling endpoints and contracts are unchanged by the redesign itself (later hardening added a per-launch session header on `/api/*`; see docs/USAGE.md), and its original views display data from `/api/snapshot` and `/api/runs`. The transport and read-only data routes added afterwards are described under Transport; the views that use them (Setup & config, Usage & cost, Evidence, Control log) are described under "Data views".

## Information architecture

Each destination is a separate view inside a responsive shell, addressed by URL hash.

| View           | Hash                                      | Purpose                                                                                                 |
| -------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Overview       | `#/overview`                              | Clickable metrics, a prioritized attention list, health, task distribution, agent glance and shortcuts  |
| Tasks          | `#/tasks?q&agent&phase&state&layout&task` | Board or list with search and filters; `task` opens the drill-down                                      |
| Agents         | `#/agents?q&status&agent`                 | Compact table, with full process, model, workspace, scheduling and usage facts in the detail pane       |
| Messages       | `#/messages?filter&q&agent&phase&thread`  | Open questions or all messages beside full thread context                                               |
| Runs           | `#/runs?lane&harness&task&run`            | Run history beside a sanitized event timeline, with follow, copy and older-run paging                   |
| Relationships  | `#/relationships?graph`                   | Communication and dependency diagram, node list, accessible relationship table and coverage metadata    |
| System & notes | `#/system`                                | Supervisor, budgets, watcher, watchdog, assignments without task cards and milestone notes              |
| Usage & cost   | `#/usage?lane`                            | Runs against caps, recent durations, reported counters, Claude cost against its cap and a 24-hour chart |
| Evidence       | `#/evidence?task&run&artifact`            | Gallery of captured screenshots and recordings; `artifact` opens the lightbox                           |
| Control log    | `#/audit?outcome&issuer&lane&seq`         | The supervisor's bounded audit trail of operator commands; `seq` opens the detail pane                  |
| Setup & config | `#/setup`                                 | Installed state, doctor-style problems with commands to copy, agents, budgets and digest                |

Primary facts sit in lists and tables. Secondary metadata moves to a detail pane or disclosure, so scanning a view does not require reading every field.

## Design choices

- **Calm cockpit.** A restrained dark sidebar, light workspace, crisp 1px borders and system fonts. No external fonts, images, CDNs or dependencies.
- **One badge vocabulary.** Tone plus text in every state; colour is never the only signal. Unknown data uses a dashed italic style, so it cannot be mistaken for a measured or healthy value.
- **Separate concerns stay separate.** Agents shows process and task progress in different columns. Configured and observed model and harness values are labelled line by line. An observed value that was never recorded reads "Not recorded". An agent named only in task data appears with no process record rather than with invented state.
- **Notices stay, in context.** Trace-safety text stays visible under the run timeline. Interpretation notes sit in "How to read…" disclosures or beside the relevant fact.
- **Inline SVG only.** Icons and the relationship diagram are inline SVG built from constant paths or `textContent`. The strict content security policy is unchanged: no inline style attributes or scripts.

## Usability changes

- Hash routing covers deep links, refresh, back and forward. Filter edits replace the history entry; opening a view or drill-down adds one.
- Sidebar links remember each view's filters but not its open item, so a section link returns to the list.
- Overview metrics and legends route to filtered views. Task, agent, thread and run links cross-navigate, and relationship selections open the matching view.
- Open questions link to their real thread, including the original question and replies.
- Snapshot updates (live or polled) re-render only the active view and preserves filters, focus, expanded disclosures, and window and pane scroll. Static filter controls are never rebuilt while typing.
- Connection state lives in the shell. A failed poll (or a stream error event) shows a banner that names the age of the retained snapshot, and data stays on screen.
- Above 1100px, details sit beside the list. Below that, the detail replaces the list with a Back link. Below 860px, the sidebar becomes a top bar with a menu button. The board scrolls horizontally inside its own labelled region, and phones default to the list layout.
- Accessibility: skip link, `aria-current`, focus moved to the view heading or detail heading on navigation, focus returned to the originating row on close, Escape closes panes and the mobile menu, visible focus, reduced-motion and forced-colors handling.
- Plain labels. Task states read To do, Assigned, In progress, Blocked, Awaiting review and Completed ("Accepted" appears only where an acceptance record exists, such as the task detail). The status filter offers "Blocked or awaiting review" for `state=attention`; filter values and URL parameters are unchanged, so existing links keep working.
- Exact times are text, not tooltips. In the dashboard, every `<time>` has a `datetime` attribute, the relative text and the exact value in a visually hidden span, so screen-reader users hear it; there is no `title` tooltip. Inside links (message rows) the exact span is `aria-hidden` to keep link names short, and the thread and detail panes carry the full value. On devices without hover (`hover: none`), the exact value is also shown as an extra visible line in cards, rows and detail fields. The run viewer emits `<time datetime>` elements whose text is the absolute formatted time, and the relationship table prints the formatted text without a `<time>` element. All of them use one formatter (`window.crewplane.formatTime`, defined in `app/time.js` and published by `dashboard.js`; the graph receives it through the `formatTime` option).
- Forced colors: selected cards, rows, run buttons, graph nodes, task-progress segments and the connection dot use `Highlight`/`CanvasText` outlines and borders instead of background or shadow cues.
- Touch: with `pointer: coarse`, buttons (including icon buttons), inputs, selects, the skip link, navigation, shortcuts and legend links are at least 44px tall. Other widths and layouts are unchanged.
- Viewport: full-height shells use `100vh` with a `100dvh` override where supported, and `scroll-padding-top` (tied to `--topbar-height`) keeps focused elements clear of the sticky mobile top bar.
- A task card shows its focus ring around the whole card (`:has(.card-link:focus-visible)`); browsers without `:has` keep the ring on the link text.
- The task-progress bar separates adjacent segments with a 1px divider and gives the neutral (To do) segment a visible border; the legend and `aria-label` still carry the counts.
- Runs: an automatically selected newest run is written to the URL with `replaceState` (no extra history entry), "Older runs" starts disabled until the first response, and a `run=` value that is not a well-formed run id shows "Unknown run id" in the timeline. A well-formed id that is not retained shows the "unavailable" message instead.
- Messages: the "show older messages" limit resets whenever the search, agent or phase filter changes. The Agent filter keeps the accessible name "Agent" and its help text ("Also shows messages sent to everyone") is attached with `aria-describedby`.
- Relationships: the live status line stays short ("12 nodes, 9 relationships"); coverage, truncation and missing-reference detail sits in a static paragraph linked from the filter input with `aria-describedby`.

## Transport

Snapshots reach the page by one of two transports, and the page always works with the weaker one.

- **Live (preferred).** `app/live.js` reads `GET /api/events` with `fetch()` and a `ReadableStream` (`EventSource` cannot send the `x-crewplane-session` header; the token never goes in a URL). `app/live-core.js` holds the pure parts, an incremental `text/event-stream` parser and the backoff function, which are unit tested. Events: `snapshot` (the `/api/snapshot` body, sent when its content hash changes and it is at most `MAX_EVENT_BYTES`, 8 MiB), `resync` (no data: the board is too large to push, so the page stays on the stream, keeps polling and shows "polling" until a snapshot fits), `error` (the same safe message `/api/snapshot` returns with 503; the stream stays open) and `ping` (a heartbeat every 15 seconds carrying the time of the last successful read, plus the id and kind of the current event). The pure event rules live in `createLiveSession` (`app/live-core.js`, unit tested): the page is `live` only after a snapshot rendered or a ping confirms the rendered one, an event that failed to render is not remembered (reconnect without `Last-Event-ID`, banner kept, pings cannot clear it), and `lastEventId` advances only for handled events. A stream silent for 45 seconds, any non-200 or non-`text/event-stream` answer, a malformed event, a render failure or a network failure ends it.
- **Polling (fallback).** The unchanged 5-second `/api/snapshot` poll. It runs whenever `store.mode` is not `live`, takes over within one 5-second tick when a live stream drops, and the retained-snapshot banner, "Disconnected" status and "Retrying every 5s" text are exactly as before. Reconnection to the stream uses exponential backoff from 1s capped at 60s with +-25% jitter, reset only after a snapshot was rendered or the stream stayed up 30 seconds (never by a connection or a ping), and an immediate poll after a drop happens only for such a stable stream, so a flapping connection cannot turn into a request per drop. A poll that began before a pushed snapshot was applied is discarded (sequence numbers in `store.applied`), and returning to a visible tab polls only when the page is not live. A tab hidden for 30 seconds aborts its stream (indicator `polling`) and reopens it with an immediate refresh when shown, freeing one of the 8 server slots. Tests inject short timings through `window.crewplaneLiveTuning` (clamped values for backoff, grace and stability), so no test waits for a production backoff. A refused ninth stream (`503`) simply stays on polling.
- **Server.** One shared computation (`dashboard/live.ts`), run sequentially about every second only while a client is connected and hashed without `updatedAt`, fans out to at most 8 clients. Event ids are `<boot>-<n>`; `Last-Event-ID` avoids re-sending an unchanged snapshot after a reconnect. A recomputation with unchanged content keeps the event id but replaces the cached body, so a client that connects later is never replayed an older `updatedAt`; the page also ignores a pushed snapshot (or heartbeat) older than the one it already shows, so "Checked" cannot go backwards when a poll answers before the stream's first event. The next computation waits `max(1s, 5 x the last computation)` up to 30s; no cheaper change signal is used because none is sound (directory mtimes miss in-place edits). A computation that spans the last client leaving is discarded, so a late joiner is never given a pre-idle snapshot. A client that is behind gets only the latest event, so at most one event is unflushed per client; the unflushed-bytes limit (16 MiB) is checked before and after every write, and a client blocked for 10 seconds is closed. Closing the server destroys every stream and clears every timer.
- **Indicator.** `#connection` keeps "Live" / "Disconnected"; `#connection-time` reads "Checked 10:00:01 · live updates" or "Checked 10:00:01 · polling", and `#connection-wrap` carries `data-mode="live|polling"`.

The data routes `/api/config` (effective caps from one source, loaded values labelled beside them; at most 64 lanes inspected), `/api/control-log`, `/api/usage` (series buckets are `null` until a retained run predates them; the global run cap is a per-lane default) and the evidence list and artifact-metadata routes feed the data views below. All are authenticated `GET` projections; see docs/CONTRACTS.md.

## Data views

Four read-only views use the data routes. None adds a control or a write: the page shows facts, explains them and links to the related views. Each fetches its route when it opens (`app/render.js` notices the view change), and Setup, Usage and the Control log also read again when the snapshot content changes, debounced (1.5s) and throttled (at most once per 8-20s), never on every poll (`app/resource.js`, unit tested with fake timers; `app/aux.js` holds the shared resources, so the Overview's attention items reuse the same answers). A failed read keeps the last answer on screen with a "refreshing failed" note and a retry button; with no answer yet it shows an alert with a retry button.

- **Setup & config (`#/setup`, `app/setup.js`, pure rules in `app/config-core.js`).** The installed state in words (not configured, installed but invalid, valid, valid with problems), a doctor-style problem list with the stable codes (`CONFIG_MISSING`, `CONFIG_INVALID`, `BINARY_*` including `BINARY_UNSAFE` with the lane and the server's reason, `INSTRUCTIONS_INVALID`, `LEGACY_LAYOUT`; an unrecognised code is shown raw as text) and what to do next. The suggested commands (`crewplane setup`, `crewplane configure --file PATH`, `crewplane doctor`) are three fixed strings, shown as text with copy buttons; the page never runs them and none is built from server data. Then a lanes table (enabled, harness, model, role, permissions in plain words, instructions presence, effective limits with "(default)" where a lane uses the shared value, passed environment variable **names** only, binary status and usage coverage), budgets as installed against loaded with the reload-pending indication, the configuration digest (12 characters with a button that copies the whole digest), the roles and stale-roles hint, the `lanesTruncated`/`problemsTruncated` markers, and two standing notices: credentials are not probed and binaries are never executed.
- **Usage & cost (`#/usage`, `app/usage.js`, `app/usage-core.js`).** Per agent: runs this hour against the cap as text, a `<meter>` (with `aria-label`/`aria-valuetext`) and a tone-plus-text badge (within, near at 80%, at, over the cap); recent run durations against the run limit; reported token counters with how many retained records reported each dimension, labelled "reported counters, not billing totals"; Claude cost against `maxCostUsdPerRun` with an over-cap flag, three-valued (over, within, no cap) and labelled as per-invocation observations. A caps notice states the single source of every cap, that the global run cap is a per-agent default (not a total) and when the loaded values differ. The 24-hour series is an inline SVG column chart (`role="img"` with a one-sentence summary, columns at most 24px with a 4px rounded end and a square base, hairline grid, one labelled peak, a native tooltip per column, the accent colour on one series so no legend box) with the same data as a table in a disclosure. Unknown is never zero: a `null` bucket is a dashed outline ("Not recorded" in the table and a legend line), a measured zero is a short baseline tick, and a null counter or run count reads "Not recorded". A "How complete is this data?" disclosure explains the coverage block. The `lane` parameter charts one agent.
- **Evidence (`#/evidence`, `app/evidence.js`, `app/evidence-core.js`, `app/evidence-link.js`).** See "Evidence gallery and blob handling" below.
- **Control log (`#/audit`, `app/audit.js`, `app/audit-core.js`).** A table of `/api/control-log` (sequence, time, issuer, action, scope and target with links to the agent, task or run, outcome badge, reason code with a plain-language explanation). Outcomes have tone and text (applied, no change, refused, out of date, not applied); refused, out-of-date and not-applied rows are marked with a left bar and a tinted row (an outline in forced colours) as well as the text. Known reason codes (the supervisor's, the dashboard's pre-queue refusals such as `CLI_ONLY`, `PIN_REQUIRED`, `LEGACY_LAYOUT`, `UNKNOWN_AGENT`, and the shared map in `app/controls-core.js`) read as sentences; any other code is shown raw as text and says it is not one the dashboard knows. Filters: outcome, issuer, agent (also from the summary counts). The API cannot page backwards, so the page reads everything retained (at most 200) once and pages older rows locally (50 at a time); it then follows newer commands with the `after` cursor every 5s while the view is open, holds exactly what the supervisor retains (entries older than `retainedFrom` are dropped, so "N of M retained" and a `?seq=` detail agree with the server), reads again from the start when the log was reset (latest sequence behind the cursor, a gap before the oldest retained entry, or a different id at the cursor or at the oldest retained entry, which also catches a reset log that has grown past the cursor), rebuilds the table only when what it shows changed (an unchanged poll keeps the rows, the pointer and focus, and does not re-announce the count), and "Follow newer commands" can be turned off, which freezes the list and offers "Show N newer commands". It says the log is capped at the latest 200 commands (and the first retained sequence when earlier ones are gone), reads "unavailable" when the supervisor state cannot be read, and says so when empty. `#/audit?seq=N` opens a detail pane (a sequence that is not retained says so); the Overview attention list shows "Commands that were not applied (N)" (refused, out-of-date, not-applied and unrecognised outcomes) for entries from the last 24 hours.

### Evidence gallery and blob handling

Artifact bytes sit behind the session header, which an `<img src>` cannot send, so the page fetches them and shows them from `blob:` URLs. The page policy therefore changes in exactly one place: `img-src 'self' blob:` and `media-src 'self' blob:`. `default-src`, `script-src`, `style-src`, `connect-src`, `frame-ancestors` and every other directive are unchanged (`default-src 'none'` still blocks frames, objects and workers; `script-src` never admits `blob:`, so a blob cannot run as script). A test asserts the exact header and that no other directive contains `blob:`; the artifact route keeps its own `default-src 'none'; sandbox`.

- **Type from an allowlist, not from the response.** `app/evidence-core.js` allows `image/png`, `image/jpeg`, `image/webp` and `video/webm`. A `Blob` is given the artifact's recorded type only when it is on that list **and** the response's `Content-Type` says the same; anything else (a different or octet-stream response, an SVG or HTML mime, an unknown type) is refused for preview. Such artifacts are download-only with a warning, and their download blob is always `application/octet-stream`.
- **Bounded object URLs.** One cache (`createObjectUrlCache`) holds 12 object URLs, growing with the number of cards on screen (cards are observed with an `IntersectionObserver` while they are in the grid) up to a hard maximum of 36, and at most 64 MiB of blobs and two videos at once. Off-screen previews are revoked first, then the least recently used and its card returns to a "Load preview" button (a revoked image is never re-fetched automatically, so scrolling cannot thrash); the open lightbox item is pinned. Everything is revoked when the view is left (`leaveEvidence`, called from `render.js` on a view change) and on `pagehide`. Tests count `createObjectURL` against `revokeObjectURL` through init-script spies.
- **Lazy, size-limited loading.** Images up to 2 MiB load as their card scrolls into view (`IntersectionObserver`, three fetches at a time); larger images wait for a Load button, videos load only from the lightbox's Load button, anything over the store's 16 MiB limit or of unknown size is never fetched, and unsupported types are never previewed. The declared `Content-Length` (when present) and the bytes read (read with a bound, so a body longer than the record is abandoned early) must equal the artifact's recorded size before a blob is made; a mismatch is shown as an error and makes no blob. "Load more" after the store pruned the cursor (a 400) reads the list again from the start (as far as was loaded, at most 200) with a notice, keeping the cards on screen. The Run filter offers the runs of the current result only; leaving the view settles queued loads and uses a generation counter so aborted loads cannot free slots they no longer hold (never more than three fetches at once).
- **Lightbox.** A modal `<dialog>` opened from the route (`artifact=ID`), labelled by its title, focus moved to the title, Tab trapped inside, Escape and the Close link close it through the route, left and right arrows step through the loaded list (replacing the history entry; they are not captured while a video or field has focus), and focus returns to the card's "View larger" link. The alt text is built from the capture metadata (route, scenario, step, viewport, outcome) with `textContent`/`alt` only. A deep link to an artifact outside the first page keeps paging (bounded) until it is found, or says it is not available. Download is an `<a download>` whose `href` is the blob URL and whose filename is fixed (`crewplane-evidence-<id>.<ext>`, `.bin` for unsupported types); the page never navigates to a blob URL.
- **Cards and links.** Kind, mime, outcome, scenario and route, viewport, size, time, task (to Tasks), run (filter this gallery) and "Runs for this task" (to Runs), the SHA-256 shortened with a copy button for the whole digest. Task detail panes show a compact "Evidence (N)" link to the gallery filtered by the task; the Run pane shows "Task evidence (N)" (the gallery is filtered by the run's task, not by the run) (`app/evidence-link.js`, count cached for 30s, "N+" when more than the 200 counted; a failed read is remembered for the same 30s, so a failing endpoint is asked once per task per cooldown, not on every render).

## Safe client state

Hash values are parsed with `URLSearchParams`, restricted to a per-view allowlist, checked against enumerations where applicable, and length-limited. Unknown views fall back to Overview. Untrusted text is rendered only through `textContent`; the dashboard does not use `innerHTML`. `localStorage` holds the board/list preference and the Preferences choices (theme, single-key shortcuts, alert settings). `sessionStorage` holds, besides the per-launch session, one small reload record (see Reload persistence). Both are validated on read and optional.

## Reload persistence

A full page reload (or history traversal back to the page) restores, once, after the first snapshot has been rendered and the relationship graph (a separate module that draws on the `crewplane-graphs` event) has drawn, so the page has its final height: the window scroll position of each view, the scroll offsets of marked panes (the task board and detail panes) and the open or closed state of the static "How to read…" disclosures. `app/reload-state.js` saves the record to `sessionStorage` under `crewplane-ui-state` on `pagehide` and when the tab is hidden; `app/persist.js` rebuilds it on read from an allowlist (known views, bounded numbers and key shapes, bounded counts), so a corrupt or hostile value is ignored (pane offsets are kept in a null-prototype object, so a stored `__proto__` key is plain data). Restored: scroll of the current view (Relationships included, for both the communication and task-dependency graphs), pane offsets only when the saved view is the current view, and open disclosures. Not restored: scroll inside the graph canvas itself, text selection, focus, and the state of disclosures that are not static "How to read…" notes. It is per tab, optional (blocked storage changes nothing), and not used after a fresh navigation, which starts at the top with disclosures closed.

## Module layout

`index.html` loads `dashboard.js` as `<script type="module">`, so the page needs no inline script and the content security policy (`script-src 'self'`) is unchanged. `dashboard.js` is only the entry: it wires the modules below and starts polling. Modules live in `app/` and import each other with relative specifiers; there are no import cycles. Lower layers reach the renderer through late-bound hooks in `store.js` (`render`, `commitSnapshot`, and `afterGraphs`, which runs after the graph event and performs the one-time reload restore) instead of importing it.

The Runs view (`run-viewer.js`, served as `/runs.js`) and the relationship diagram (`graph-viewer.js`, `graph-renderer.js`) are separate scripts that talk to the shell through `window.crewplane`, `window.crewplaneFetch` and the `crewplane-route` and `crewplane-graphs` events. `tests/docs.test.ts` fails if a module under `src/engine/dashboard` is missing from this table or the table names a module that does not exist.

**First load.** `index.html` carries a generated block of `<link rel="modulepreload">` entries for the whole module graph, written by `scripts/embed.ts` from the imports of the page's module scripts; the CI "assets up to date" step covers `index.html` too. The links are same-origin `src` URLs, so the policy is unchanged. Measured with a throttled profile (see STATUS.md), they cut the import chain from four levels to one, but the first render did not improve: the server speaks HTTP/1.1, so the browser's six connections per host, not the dependency depth, set the load time. They are kept for HTTP/2 front ends and slower first round trips; bundling would be the real fix and is outside this design (no build step).

## Embedding

`scripts/embed.ts` scans `src/engine/dashboard` recursively for `.html`, `.js` and `.css` files (never `*.test.*` or server-side TypeScript such as `graph-builder.ts`), sorts the names, copies each to `src/engine/assets/<name>.txt` and writes `src/engine/assets.ts` (a generated file, excluded from Biome). The assets directory is rebuilt from scratch on every run, so removed files do not linger. Adding a module is just adding a file. The server routes `/` to `index.html` and `/<name>` to each embedded name (plus `/runs.js` for the run viewer) by exact match against that set, with the content type taken from the extension (`text/javascript` for modules) and `nosniff` kept; every other path, including traversal attempts and query strings, is a 404. Tests check that the embedded set equals the directory scan, that every import specifier in an embedded script resolves to an embedded file, and that the server serves or refuses paths accordingly. CI reruns the embed script and fails if `git status --porcelain` shows anything under `src/engine/assets` or `assets.ts`: stale or hand-edited copies (modified), copies never committed for a new source (untracked), missing copies, and orphan copies whose source is gone (deleted by the rebuild).

## Operator controls

The controls layer (`app/controls.js`, pure rules in `app/controls-core.js`) exists only when `GET /api/controls` says enabled and the page holds the controls token; otherwise there is no UI change, no dialog element and no control request. The sidebar footer says which mode applies.

- Contextual placement: Agents detail (Pause/Resume, Retry, Nudge, and per task Approve/Deny, Retry with new session, Confirm cleanup and retry, Cancel run), Runs (Cancel run for the selected active run), Overview attention and Messages ("Decisions waiting for you" with Approve/Deny), System (Stop supervisor). Buttons appear only for verbs the read model says are meaningful.
- Every action opens one modal `<dialog>` (no inline styles or handlers, so the CSP is unchanged) labelled by its title and described by the sentence that restates what will happen and which revision, run or session it is pinned to. Focus moves to the note field (or the first field), Tab wraps inside the dialog, Escape or "Keep as is" closes it, and focus returns to the trigger (found again by key when a snapshot rebuilt it). The note is required exactly where the CLI requires text; confirm-cleanup needs an explicit acknowledgement checkbox; cancel and stop need the target name or `stop` typed. Problems are announced in an `alert`; invalid fields get `aria-invalid`.
- Each dialog creates one request id when it opens and every submit from it, including a retry after a failure, carries that id, so the server queues it at most once. If the request fails without an answer the dialog stays open and says "The request may not have been queued", checks `/api/control-log` for that id (closing and showing the recorded outcome if it is there) and otherwise offers the retry. Pause, Cancel run and Stop are never blocked by the rate limit or queue cap.
- After confirming, a polite live region shows `Queued: ...` and then the recorded outcome with its reason code in plain language (applied, no change, refused, out of date), refreshing the board and pins. Stale outcomes say the agent changed after the page was opened. If nothing is recorded within 30 seconds it says so and that a command is refused as stale if the supervisor starts later.
- Accessibility: 44px minimum targets, visible focus, text and borders (not colour alone) distinguish outcomes, forced-colors rules draw explicit borders, and all dynamic text uses `textContent`.

## Limitations

- The dashboard is read-only unless started with `--controls true` and opened from the controls URL; there are no reply actions and nothing starts agents or the supervisor.
- Browser reload restores the view, filters and open item, plus scroll and the "How to read…" disclosures (see Reload persistence). Other disclosures, such as the task card text, are preserved across polls but start closed after a full page load. The run timeline loads after the first render, so its scroll position after a reload is best effort.
- Run timelines keep the latest 500 events client-side, and tailing fetches 100 events per poll.
- The all-messages list renders 100 rows at a time, with a button to show more.
- The relationship diagram is an aid and never draws more than 50 nodes and 100 edges at once; the server model behind clusters, focus and paging is itself capped at 1,064 nodes (1,000 tasks plus 64 lanes, the most a valid input holds) and 3,000 edges (the rest is counted as truncated). Relationships to something that is not a node (an archived task, a recipient that is not a lane) stay in the table and in the missing-reference count, as in the server's own graph. Keyboard and screen-reader users use the node list and table.
- Evidence is a gallery of captured files, not a capture tool: nothing is recorded, uploaded or deleted from the page. Videos load only on request and play from memory (a 16 MiB bound), so very long recordings are better opened from the evidence store.
- The Control log shows at most the latest 200 commands the supervisor retains, and the page keeps no more than that. Setup & config reports what is installed and what the file system says about binaries; it cannot tell whether a harness is signed in or works.
- The usage chart has native per-column tooltips and a data table, not a custom hover layer.
- Usage figures are retained counters, not billing totals. Coverage stays limited to what the read model supplies; hours the retained history does not cover read "Not recorded".

## Command palette

`app/palette.js` (UI), `app/palette-core.js` (what is searchable) and `app/search-core.js` (pure ranking). Opened by the Search button, `Ctrl`/`Cmd`+`K` (also by the physical K key on layouts that type no Latin letter there, such as Russian or Greek) or `/` (however the layout types it, with or without Shift, as on German and French keyboards). A modal `<dialog>` (shared `app/dialog-kit.js`: `showModal`, `aria-labelledby`, Tab trap, Escape, focus returned to the opener) holding a `role=combobox` input over a `role=listbox`, with `aria-activedescendant`, Up/Down/Home/End/Enter, a polite result count and 44px rows. It indexes only data already loaded: tasks (id, title, owner, phase), agents, thread roots (first line of the message), runs the Runs view loaded, artifacts the gallery loaded, every view and these ten commands: Show open questions, Show blocked tasks, Show tasks awaiting review, Show running agents, Show stale agents, Show refused commands, Show the task dependency graph, Show all messages (each opens a filtered view), Keyboard shortcuts and Preferences (each opens its dialog). A test checks that every command has a handler in `dashboard.js` or a valid route, that the index keeps the dialog commands, and the browser suite runs both dialog commands with Ctrl+K, typing and Enter. No request is made. Ranking per term: exact > prefix > word prefix > substring > subsequence; every term must match; ties keep kind order then supplied order; case, diacritics and Unicode format characters (bidi controls, zero-width characters, soft hyphen, the byte order mark) fold away, and the text the palette draws has the reordering and invisible ones removed, so what is matched is what is shown (`unicode-bidi: isolate` on the rows as well); the query is cut to 100 characters and 6 terms and is never turned into a pattern. Results are at most 50, the index at most 3,000 tasks, 3,000 threads, 500 runs and 500 artifacts. Results navigate through the hash router; all text is `textContent`. Performance is asserted by counting field reads (doubling the entries at most doubles them) and by budgets of about ten times the measured warm time.

## Keyboard shortcuts

`app/keymap-core.js` is the single table and a pure resolver; `app/shortcuts.js` wires one `keydown` listener and builds the `?` overlay from the same table. Bindings: `Ctrl`/`Cmd`+`K` and `/` (search), `?` (this list) and `g` then one letter (a view). The only modified binding is `Ctrl`/`Cmd`+`K`. Bare keys act only when focus is not in an input, textarea, select, editable region or composite widget (`combobox`, `listbox`, `grid`...), no dialog is open and single-key shortcuts are on; chords time out after 1.5 s; key repeat and IME composition are ignored and cancel a chord. Layouts: `/` is matched by the character produced, so Shift does not matter; `Ctrl`/`Cmd`+`K` is matched by the produced letter, and by `event.code === "KeyK"` only when the produced character is not a Latin letter (so a Dvorak `t` on the K key is not Ctrl+T's). Tests cover German, French, Dvorak, Russian and Greek cases. Tests assert no duplicate sequences, that every view has exactly one chord, that modified or shifted keys never trigger and that nothing binds Tab, Enter, Space, Escape or arrows. Turning single keys off (overlay or Preferences) is stored in `localStorage` and leaves `Ctrl`/`Cmd`+`K` and the Search button.

## Themes

`theme.css` defines every colour token once: light (default), dark under `@media (prefers-color-scheme: dark)` with `:root:not([data-theme="light"])`, and an identical dark block under `:root[data-theme="dark"]`. `dashboard.css` and `graph-renderer.css` use only those tokens (the graph file with light fallbacks); no raw colour remains. A choice of System, Light or Dark is saved as `crewplane.theme` (System = no key). `theme-boot.js` is a tiny external blocking classic script in `<head>` (no inline script, CSP unchanged) that sets `html[data-theme]` before first paint; `<meta name="color-scheme">` lets form controls follow. `theme.test.ts` independently computes WCAG ratios for every foreground/background pair in both themes (text 4.5:1, graphics and focus 3:1), checks the two dark blocks are identical, that every `var()` is defined and that no raw colour is left. Known limit: hairline input borders (`--border-strong`) keep the earlier design's lower contrast in both themes; they are not relied on alone (inputs also have a fill and labels). Forced colors are handled with system colours, as before. A theme chosen in another tab (a `storage` event) is applied and the pressed state of the theme buttons follows. Printing: an `@media print` token block in `theme.css` repeats the light values (a test keeps it identical to the light block) at a specificity above both dark blocks, and `dashboard.css` hides the skip link, sidebar, dialogs, toolbars and buttons while keeping headings, text and tables (header rows repeat, rows do not split).

## Preferences

One dialog (`app/preferences.js`, opened from the sidebar; the theme switch is also in the sidebar): theme radios, "Single-key shortcuts", alerts and "Reset saved view state" (clears the remembered Tasks layout and the reload memory only; theme, shortcut and alert choices are kept). Every control is a labelled native input, applies at once and degrades without storage.

## Alerts

`app/notify-core.js` (pure) derives events by comparing consecutive snapshots (and the control log, once it has been read): new open question or request, task newly blocked, agent newly paused (an operator hold is not news; the read model cannot tell a failure pause from a decision pause without the controls layer, so both read "paused"), command newly refused, out of date or not applied, and the supervisor stopping unexpectedly. The first observation of each category is a baseline and never alerts; an id alerts once and stays remembered (at most 200 per category) after it disappears; categories can be switched off and still learn what exists.

_Supervisor._ "Not running" is often what the operator asked for, so it alerts only when all of these hold: it was seen `running` since the last alert or clean stop; no stop explains it (a `draining` snapshot, or an applied `stop` command in the control log newer than the last running snapshot); it still looks down at a second observation at least 3 s after the first (`stale` or `stopped`; a flap running, stale, running never reaches two); and the last supervisor alert was more than 10 minutes ago. With the control log not read yet, `stopped` is not announced (a missing answer proves nothing); `stale` does not need it. `app/notify.js` schedules one recheck (it re-reads the log) so the second observation happens even when nothing else changes. Stops issued from the CLI do not appear in the dashboard's control log, so a CLI stop can still read as unexpected after a stale period; that remains a limit.

_Delivery._ `app/notify.js` shows a count in the tab title and, only with permission granted after an explicit click on "Enable desktop alerts", a notification with a fixed tag. Clicking a notification focuses the tab and opens a fixed view for its first category (open questions, blocked tasks, agents, refused commands or Overview; never a URL taken from data). Both stay quiet while the tab is visible and focused unless "also alert while this tab is open" is on. Text is counts and fixed phrases; no ids, titles or bodies. Defaults are off.

_Background tabs._ A hidden tab suspends its event stream after 30 s and pauses the 5 s poll. With a title count or desktop alerts on, `app/hidden-poll.js` keeps reading `/api/snapshot` about once a minute (60 s, spread +-20% so open tabs do not synchronise; tests shorten it with `crewplaneLiveTuning.hiddenPollMs`), only while the tab is hidden and not receiving the stream, so the same comparison runs. Turning alerts off stops the timer and aborts a request in flight; with alerts off a hidden tab makes no requests. Browsers may still throttle timers in long-hidden tabs, so an alert can arrive late. Limit: nothing is observed while no tab is open.

## Relationship graph at scale

The server still sends the capped `graphs`; `graphModels` adds the larger compact model (see docs/CONTRACTS.md). `app/graph-scale.js` (pure) projects it into at most 50 items and 100 edges: **clusters** (collapsed groups are one node and merge their edges; expanded ones show a header plus members; each is a button with `aria-expanded`), **focus** (a node plus 1 to 3 hops, from each node's Focus button or `focus`/`hops` in the URL) and **paging** by priority (blocked or stale or paused work and open questions first), Previous/Next 50 with a polite "Page n of m". Truncation text keeps the same "Truncated: n nodes, m edges" wording and adds what is on this page. The renderer independently cuts its input to 50 nodes and 100 edges, so a hostile snapshot cannot grow the DOM; a test feeds it 2,000 nodes and 5,000 edges. The accessible node list and table stay in sync with the diagram. Relationships to ids that are not model nodes pass through as direct edges under the same 100 edge cap; a differential test compares the server's `graphs` with the page's projection of the model on random boards with missing references, for both views. The model is compact (version 2: node indexes, a shared table for labels, threads and times, ids only where a node is missing; sizes in docs/STATUS.md) and the page also reads the first, tuple-by-id form. Layout: the drawing wraps at the canvas width (180 units per column; a long dependency chain continues in bands below), and with grouping on, collapsed clusters fill rows left to right while an expanded cluster takes its own rows with its header first and its members beneath it, so what was opened sits next to its control; the layout follows the canvas width. Grouping is linear in the group size (a 5,000 node group projects in a few milliseconds).
